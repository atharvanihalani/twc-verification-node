What is Telemetry-based Verification?

Telemetry-based Verification uses real time telemetry data from GPUs to verify whether their active workloads agree with what has been declared. It is an unproven, hardware-light, quickly-deployable approach to Compute Verification.

Telemetry data refers to the ‘metadata’ of a GPU. For example- a GPU’s power utilization, or the percentage of HBM that’s occupied, or the number of bytes flowing over the scale-up interconnect domain, etc.

Different workloads exhibit different patterns of telemetry. For example- pre-training is more compute intensive, which translates to higher power utilization. Alternatively, inference happens in pods- which means you see high communication within a pod, but very little across pod boundaries. Ultimately, the question is- Can we use these telemetry signatures to verify that workloads are compliant with a pre-existing agreement?

Verification Architecture

Terminology

  • Prover: The datacenter operator who needs to prove their workloads are compliant with an AI agreement. Assumed adversarial.
  • Verifier: The Independent Verification Organization that responsible for verifying compliance with the agreement.
  • Verification Node: A physical, tamper-resistant server, that receives data from the Prover’s GPUs, runs a classifier to ensure compliance, and reports this information to the Verifier.
  • Collectors: Programs running on each of the Prover’s GPU nodes that report telemetry data to the Verification Node

This architecture must guarantee at least two security properties

  • Integrity of information received by the Verifier
  • Confidentiality of sensitive information gathered from the Prover

To ensure the integrity of reported information, we must guarantee the integrity of (a) inbound information to the Verification Node, (b) the Verification Node itself, and (c) outbound information from the Verification Node to the Verifier. For (a) we’re assuming it will be possible to sign telemetry on the GPU die itself, before the prover has a chance to spoof it.1 For (b) we rely on tamper-proof or tamper-evident enclosures around the Verification Node, to prevent the Prover from physically reading the private key, or otherwise tampering with the node. And for (c), we assume the Verification Node signs outbound traffic.

The Prover’s telemetry must also be kept confidential. Side-channel analysis on telemetry can reveal sensitive IP [add links], which the Prover would not want to leak. So, all telemetry processing must be done on-site. The Prover should also have visibility into outbound traffic, to ensure the Verification Node isn’t exfiltrating sensitive information. Additionally, any reported information must be minimal, and the format must be pre-agreed, to minimize risks from any steganographic smuggling.

This architecture is hardware-light. It requires the install of one physical Verification Node, within a tamper-resistant / evident enclosure. Because telemetry is attested, it can be sent over the Prover’s networking infrastructure, with no specialized hardware sensors required. Installing a tamper-resistant node is also a problem with known solutions, so it doesn’t require any time for innovation.

This verification scheme should also be complemented with physical inspections and other approaches (eg. PoW-based approaches) to cross-verify that compute is being used as agreed. Also, this approach doesn’t account for (a) undeclared compute within the datacenter (which hopefully physical inspections can catch), or (b) workloads being split across multiple facilities, in a way that evades monitoring at each individual one.

Prototype Details

I implement this verification node in my demonstration. This is a server endpoint running in a fly.io container. You can install a collector script on your own GPUs [link] to report telemetry information to this node.

Collector.py sends telemetry to the verification node at 1 hz. This telemetry is polled from NVML, and includes per-GPU power draw, memory bandwidth, and networking data, amongst other fields [link].

There are two types of data the Collector receives- telemetry and declared workloads. Telemetry is reported at the node-level- ie. the collector can receive telemetry from multiple nodes simultaneously, as it would in a real deployment. It collates and overlays them on a graph [link]. (For prototype purposes, it’s hard to find multi-node clusters for running separate workloads and reporting telemetry separately. So I’ve also enabled sub-nodes as the unit of telemetry reporting, within in single node. So it’s not the 8x box that’s the unit at which telemetry is sent, but it’s one box, divided into eg. 4 + 4 GPUs,with the two halves reporting data separately.)

The declared workload is reported at the cluster-level. A second script runs on the head node to report the slurm logs [link]. The Collector then parses this, and represents this as a graph [insert img?] of GPUs over time. (In practice, Slurm is mostly used for research experimentation. Serving is orchestrated with Kubernetes, and pre-training doesn’t really need an scheduler. That being said, a “scheduler” stands in for “source of ground truth” in this demo. And the reported format might be different, but the Verifier Node will still end up with a similar graph for declared workloads.) The Verifier Node then uses the telemetry to confirm whether what’s running matches what was declared.

This demonstration verifies compliance with three rules. (a) You’re not running an undeclared load, when the GPUs are meant to be inactive, (b) you’re not running training when you claim to be running inference, and (c) you’re not sharing information across partition boundaries. Open Problems

  • Signing telemetry, dealing with verification authenticity
    • PKI, nonce provisioning, verifying firmware integrity periodically, etc
  • Cross-node telemetry
    • NVML doesn’t expose infiniband data
  • Ensuring no dark compute within a datacenter
  • Workload range / realism
    • Pre-training on a single node is not realistic.
  • Realistic red-teaming (sparse training, etc)
  • This is within a single node. Doesn’t account for cross-node telemetry.
  1. This is not possible with current Nvidia firmware. This prototype assumes either it can be enabled with a firmware upgrade, or there exist other ways to fingerprint the telemetry. Another way to guarantee integrity of inbound data is through retrofitted hardware sensors (eg. network taps, or power monitors). ↩
