A Working Prototype

Telemetry-based verification is a currently-unproven, hardware-light, quickly deployable approach to compute verification for Pacing the Frontier. This is a working prototype that can be scaled up to run in a production datacenter.

There are two uncertainties to scaling this up.

  • Can you trust reported telemetry to be unmodified?
  • How adversarially robust is this classifier with real workloads?

Lucid Computing is working on both of these. Reach out if you want to learn more.

What is Telemetry-based Compute Verification?

Telemetry-based verification uses live GPU telemetry to verify whether a cluster’s active workloads comply with pre-agreed rules.

Telemetry is GPU metadata. For example, power utilization, HBM bandwidth, network data over NVLink, etcetera. Different workloads have different telemetry patterns; we can use these patterns to understand properties of the workloads.

For example, inference is conducted in pods of o(100) GPUs. This means there’s a lot of communication within a single pod, but very little across pod boundaries. Alternatively, pre-training involves highly frequent gradient updates and frequent checkpointing. These manifest as periodic power dips, that are synchronous across many GPUs.

Consistency Checking, not Classification

Previous literature has focused on using telemetry to ‘reverse engineer’ the workload that was running. This faces problems when you scale it up:

  • How do you classify multiple workloads? In a real cluster, your classifier receives unstructured data from o(100K) GPUs. Before it can classify the workloads, it needs to segment this data into different workload partitions- which is a harder problem than the classification.
  • Sheer difficulty of multi-class classification. Verification solutions must have negligible error, especially if used for high-stakes agreements. It’s far easier to check for anomalies, or deviations from declared workloads, than to precisely classify workloads without conditioning on any information.

This approach requires the Prover to declare their intended workloads ahead of time, and checks them against reported telemetry.

Verification Architecture

Terminology

  • Prover: The datacenter operator who needs to prove their workloads are compliant with an AI agreement. Assumed adversarial.
  • Verifier: The Independent Verification Organization that’s responsible for verifying compliance with the agreement.
  • Verification Node: A physical, tamper-resistant server. It receives data from the Prover’s GPUs, runs a classifier to ensure compliance, and reports this information to the Verifier.
  • Collectors: Programs running on each of the Prover’s GPU nodes that report real-time telemetry to the Verification Node.

This architecture must guarantee at least two security properties

  • Integrity of information received by the Verifier
  • Confidentiality of sensitive information gathered from the Prover

To ensure the integrity of reported information, we must guarantee the integrity of (a) inbound information to the Verification Node, (b) the Verification Node itself, and (c) outbound information from the Verification Node to the Verifier. For (a) we’re assuming it will be possible to sign telemetry on the GPU die itself, before the prover has a chance to spoof it. (This is not possible with current firmware versions, though a firmware upgrade might enable it.)1 For (b) we rely on tamper-proof or tamper-evident enclosures around the Verification Node, to prevent the Prover from physically reading the private key, or otherwise tampering with the node. And for (c), we assume the Verification Node signs outbound traffic.

The Prover’s telemetry must also be kept confidential. Side-channel analysis on telemetry can reveal sensitive IP2, which the Prover would not want to leak. So, all telemetry processing must be done on-site. The Prover should also have visibility into outbound traffic, to ensure the Verification Node isn’t exfiltrating sensitive information. Additionally, any reported information must be minimal, and the format must be pre-agreed, to minimize risks from any steganographic smuggling.

This architecture is hardware-light. It requires the install of one physical Verification Node, within a tamper-resistant / evident enclosure. Because telemetry is attested, it can be sent over the Prover’s networking infrastructure, with no specialized hardware sensors required. Installing a tamper-resistant node is also a problem with known solutions, so it doesn’t require any time for innovation.

This verification scheme should also be complemented with physical inspections and other approaches (eg. PoW-based approaches) to cross-verify that compute is being used as agreed. Also, this approach doesn’t account for (a) undeclared compute within the datacenter (which hopefully physical inspections can catch), or (b) workloads being split across multiple facilities, in a way that evades monitoring at each individual one.

Prototype Details

This demo implements the above architecture. The Verification Node / Collector is running in this fly.io container, that accepts streamed telemetry input from collector.py. For this demonstration, I’m replaying locally stored telemetry data that was generated from pre-training and inference workload variants. I also implement a classifier that consumes telemetry from a rolling 60s window to check compliance with three rules.

Collector.py samples telemetry at 1-10 hz, and sends this batched to the verification node. This telemetry is polled from NVML, and includes per-GPU power draw, memory bandwidth, and networking data, amongst other fields.

There are two types of data the Collector receives- telemetry and declared workloads. Telemetry is reported at the node-level- ie. the collector can receive telemetry from multiple nodes simultaneously, as it would in a real deployment. This is overlaid on a graph [link].

The declared workload is reported by the scheduler running at the cluster-level. A second script runs on the head node to report the Slurm logs [link]. The Verifier Node then uses the telemetry to confirm whether what’s running matches what was declared.

What workloads am I running?

I’m running pre-training and inference workloads on one 8x Nvidia GPU node. This is for simplicity’s sake- in practice, workloads would also include post-training, evaluations, experimentation, etc. I’m using an 8x HGX GPU node because HGX is the form factor used for datacenter servers (as opposed to PCIe / NVL nodes). Also, production workloads are run on multiple nodes, but it’s hard to find multi-node availability through cloud providers, so I run workloads on single nodes.

For inference, I’m using vLLM to serve DeepSeek V4.1 Flash across different serving configs. vLLM is an inference engine that’s popular among model providers, and is representative of how models are served in-practice. Benchmarking inference also requires synthetic user data- for this, I use SemiAnalysis’ AgentX traces. These represent realistic serving traffic for agentic workloads, and are used for SemiAnalysis’ public InferenceX benchmarks.

For pre-training, I use TorchTitan to pre-train Llama 3 8B. TorchTitan is PyTorch’s own reference codebase for pre-training LLMs, and lets you combine many common training optimizations- including parallelisms, sharding, recomputation, etc. Real pre-training would run on more nodes and have larger batch sizes.

How are my classifiers implemented?

I implement three rules for this demonstration: GPUs never run undeclared loads, there’s no data flowing across declared partitions / pod boundaries, and workloads declared inference are not doing training.

Undeclared Workloads: If your scheduler doesn’t declare a workload, your GPU shouldn’t run anything. Classification rule- is your power utilization above baseline (200W for Hopper GPUs, 300W for Blackwells)?

Cross-Partition Traffic: Inference takes place in pods of o(dozens) GPUs. If a partition is truly doing inference, there should be no traffic flowing across the east-west GPU fabric- because inference pods are independent units that don’t need to communicate. Classification rule- is network data above a low threshold (1MB/s).

Hidden Training: If you declare a workload as inference, you shouldn’t be doing training instead. Inference is communication intensive, because (a) autoregressive decoding means you spend more time moving weights between HBM and the logic dies, and (b) you’re also moving the large KV-cache between HBM and logic. Classification rule- is tensor core utilization above 40%?

These simple thresholds told apart every workload I recorded, with wide margins. None of the workloads were trying to hide, so robustness is untested; but a wide margin is a good sign for a classifier that is robust enough in practice.

Open Problems

As mentioned above, the two big uncertainties are (a) signing telemetry, and (b) adversarial robustness. If the telemetry is unsigned, the prover can likely spoof it before reaching the classifier. Also, these current rules have not been sufficiently red-teamed.

Besides these, a production setup would also include: verifiying signed telemetry, nonce provisioning, PKI; redundancy in system design (eg. multiple Verification Nodes); mechanisms to escalate failures (eg. what happens if GPUs temporarily go dark?); and physical tamper-evident servers running over large clusters.
